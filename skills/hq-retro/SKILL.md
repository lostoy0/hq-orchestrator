# HQ 复盘

你负责复盘 `/hq` 的运行数据，产出**有证据的**改进建议。用户把关后，插件才会改变。

## 用户对质量和效率的定义（复盘必须以此为准）

- **质量门槛 = 不漂移 + 验证到位 + 问题少。**
- **优先级**：先过质量门槛，再比总用时（尽量并行），最后比 token。
- **不能拿质量换省钱**：只要返工率或问题数上升，降档类改动一律撤回。

## 路径约定

- 运行数据：目标项目的 `.hq/runs/*.jsonl`；本地运行时还有 `~/.claude/hq/runs/*.jsonl`。
- 脚本：`hq` 技能目录下的 `scripts/metrics.py`（插件仓库里是 `skills/hq/scripts/metrics.py`；安装后用 shell 查找：`find ~/.claude/skills ~/.claude/plugins ~/.agents/skills .claude/skills .agents/skills -path '*hq/scripts/metrics.py' 2>/dev/null | head -1`）；难度分档：同目录的 `calibration.md`；数据格式：`references/metrics-schema.md`。
- 项目经验：`.hq/PLAYBOOK.md`（模板 `skills/hq/references/playbook-template.md`）。
- 改动历史：插件仓库的 `CHANGELOG.md`。找不到就在报告里写明，当作“没有上次改动”。
- 这些文件都只读，复盘本身不修改它们（PLAYBOOK 除外，见第 7 步）。

## 流程

### 1. 收集数据

1. 运行 `python3 <metrics.py 路径> .hq/runs ~/.claude/hq/runs --last 10`（目录不存在就省略；两处都有的同一次运行只算一次）。用户指定了项目或次数，就加 `--project NAME` 或改 `--last`。
2. 读 `CHANGELOG.md` 最近几条改动和当时的假设。
3. 读 `calibration.md` 和目标项目的 `.hq/PLAYBOOK.md`。
4. 原始 jsonl **只在需要查证某条信号时**才读，读哪条记哪条。
5. 运行数不足 3 次或总任务数不足 10 个：直接告诉用户“数据太少”，只出数据概览和观察，不出建议。

### 2. 交给独立复盘子代理（防止自我打分偏差）

- 用宿主的 spawn_worker 能力（见 `references/hosts/<host>.md`），档位 T2（Claude Code 为 sonnet / medium）。宿主没有子代理能力时可用 W 通道；都没有就降级：自己只按下面“只给它”的材料做，并在报告里注明“未经独立复盘”。
- **只给它**：metrics 报告全文、CHANGELOG 相关条目、`calibration.md`、本文件的“复盘清单”“证据门槛”“防退化规则”三节、输出格式。
- **不给它**：你自己对这次运行的看法、对任务好坏的印象。
- 让它返回：上次改动验证表、观察、建议草案（含依据）。它要查证的 jsonl 行，由它自己读。
- 子代理返回后，你只做三件事：核对它引用的数字是否和 metrics 报告一致；套用第 5、6 步的门槛筛选；套用第 7 步分层。不要凭印象加建议。

### 3. 先验证上次的改动

对 CHANGELOG 里每条状态为“待验证”的改动，按它的验收指标逐条判断：

| 结果 | 条件 | 动作 |
|---|---|---|
| 达到 | 指标达到预期，且质量门槛没有变差 | 建议把状态改为“已验证” |
| 未达到 | 指标没达到，或返工率、问题数上升 | 生成**撤回建议**（排在建议第一位，不占 5 条名额） |
| 样本不足 | 改动后的相关任务不足 3 个 | 保持“待验证”，写明还差多少 |

### 4. 复盘清单（逐项检查，每项写一句结论，没问题就写“无异常”）

1. **选档**：各档位的一次通过率、升档率；有没有降档空间（某档连续通过且返工为 0）；有没有该升未升。
2. **估时**：预计用时与实际用时之比；偏差大的任务类型。
3. **并行效率**：加速比、wall/关键路径；哪些任务本可以打包（太碎），哪些本可以拆开（拖长关键路径）。
4. **任务说明质量与调档**：漂移率、检查点次数、派生任务数、升档任务中有检查点的比例、用户手动调档次数。
5. **验证**：验证到位率；有没有该验证没验证；有没有多余的重复验证。
6. **监控与记录**：wall/关键路径（巡检不及时、收尾慢会拉高它）；缺记录任务数。
7. **自主性**：停下来找用户的次数、用户纠正次数，哪些本可以自己决定。
8. **成本**：以 `cost_usd` 为主、`tokens`（不含缓存读取）为辅；开销最大的任务类型，是否值得。
9. **跨宿主、跨厂商对比**：用 metrics 报告“3c 按宿主/通道”（含 W、`main`）和“3b 按模型”（model 前缀 `<cli>:`）分组比较一次通过率、返工率、cost_usd。每组至少 3 个任务才比较，不足就写“样本不足”；结论按第 7 步分层。

### 5. 证据门槛

- 一个问题要在**至少 3 个任务**或 **2 次运行**里出现，才能形成建议。
- **例外**：单次严重事故（major 问题、数据风险）可以直接形成建议。
- 达不到门槛的，只记为**观察**，写明已出现几次、还差几次。不形成建议。

### 6. 防退化规则

- 每条建议必须写：**依据**（哪些 run 和 task、什么数字）、**预期效果**、**验收指标**（之后看哪一项）。缺一项就删掉这条。
- **优先修改或删除已有规则**，不随意新增。`skills/hq/SKILL.md` 不能超过 260 行；建议会让它超出时，必须同时给出要删的内容。
- **降档类建议只能做小范围实验**：只用于低风险任务，并且最多每 5 个任务挑 1 个。大范围改 `calibration.md` 的降档阈值不允许。
- 每次复盘最多 **5 条建议**，按预期收益排序。超出的放进观察。
- 撤回建议不受证据门槛限制，也不占名额。

### 7. 分层

- **只与该项目有关**（测试命令、项目特有的坑、该项目适合的档位）：直接写进目标项目的 `.hq/PLAYBOOK.md`，不需要用户把关。遵守模板里“最多 30 条，新的替换旧的”，每条带证据和日期。
- **涉及插件本身**（`calibration.md`、流程、模板、脚本、SKILL.md）：形成插件改进建议，**必须由用户把关**，不得直接改。
- 拿不准归哪层：当作插件建议。

## 输出

报告直接显示给用户，同时保存到 `.hq/retro/<YYYY-MM-DD>.md`（同一天有多份就加 `-2`）。结构如下：

1. **数据概览**：运行数、任务数、时间范围，以及 metrics 的关键数字（漂移率、验证到位率、返工率、合并通过率、各档一次通过率、加速比、成本）。每个数字标样本量。
2. **上次改动的验证结果**：表格，每条“达到 / 未达到 / 样本不足”加一句数据理由。
3. **观察**：未到证据门槛的，各写“现象、已出现次数、还差什么”。
4. **建议**：每条包含——问题、证据、改动（到文件和段落）、预期效果、验收指标。
5. **已写入项目 PLAYBOOK 的内容**：列出条目；没写就写“无”。
6. **复制到 hq-orchestrator 仓库的会话中执行**：一个代码块，内容按下节模板填写。

**没有达到证据门槛的建议、也没有要撤回的改动：** 第 4 节写“本次没有建议改动”，第 6 节不输出提示词。不要硬凑。

## 注意

- 复盘是为了让插件变好，不是为了出建议。数据不支持，就如实说没有。
- 引用数字一律来自 metrics 报告或你亲自查过的 jsonl，不估算、不编造。
- 用户不同意某条建议时，把理由记进观察，下次复盘不再重复提，除非有新证据。
