# 子会话任务说明模板

子会话只能看到这份说明，看不到主会话的任何上下文。所以下面每一项都要写全，不要写“如前所述”这类依赖上下文的话。

```
# 任务 <id>：<一句话标题>

## 目标
<要达成什么、为什么要做。1 到 3 句话>

## 背景与入口
- 仓库/目录：<路径或 GitHub URL>，基线分支 <branch>
- 先读这些：<文件路径:行号、文档链接>
- 已经排除的方向：<主会话已知不行的路，避免重复踩坑>

## 范围
- 只允许修改：<文件或目录列表>
- 禁止修改：<共享接口、配置、其他任务的归属文件>
- 不做：<明确不在本任务范围内的事>

## 验收标准
1. <可检验的条件>
2. ...

## 验证命令（交付前必须跑，并贴出输出末尾 30 行）
<例如 npm test -- path/to/spec --maxWorkers=2>

## 资源限制
- 并行度不超过 <N>（make -j<N> / pytest -n <N> / --maxWorkers=<N>）
- 不要启动常驻服务；如果必须启动，用完立刻关掉
- 预计时长 <X> 分钟。超过 2 倍还没做完，就停下来按“卡住”的方式交付

## 分支与提交
- 在分支 hq/<id> 上提交，提交信息以 "[hq/<id>]" 开头
- <远程子会话：完成后推送到 hq/<id>> <本地 worktree：只提交，不推送>
- 不开 PR，不改其他分支

## 遇到问题时
- 需求有歧义：选最保守的解释继续做，并在报告里列出。如果歧义会导致返工，就停下来提问
- 提问方式：<远程：用 send_message 发给主会话 <主会话 session_id>> <本地：直接返回，状态写 NEEDS_INPUT>
- 禁止为了让测试通过而删除或跳过测试、放宽断言

## 交付格式（最后一条消息必须严格按这个格式）
STATUS: DONE | PARTIAL | NEEDS_INPUT | FAILED
BRANCH: hq/<id> @ <commit sha>
CHANGES: <文件列表与一句话说明>
VERIFY: <运行的命令和结果，附输出末尾>
RISKS: <可能的副作用、没覆盖到的情况>
QUESTIONS: <需要主会话或用户决定的事，没有就写 none>
```

## 写说明的要点
- 能给出文件路径、函数名、错误信息原文，就不要只做描述。
- 只陈述事实，不要把你的猜想当结论交给子会话（“我怀疑是 X”可以写，“问题就是 X”不要写），否则子会话容易只去证实它。
- 审核类子任务只给代码位置和验收标准，不给实现者的报告，这样才能独立判断。
