# HQ 计划阶段（/hq-plan）

把需求变成能直接交给 `/hq` 执行的版本计划：分几个版本、每个版本做哪些任务、任务之间的依赖、每个任务的验收标准和预估档位。**本阶段不写代码。**

## 先读

1. 找 hq 技能目录 `<hq>`：本文件同级的 `../hq/`（里面有 `SKILL.md`）；没有就读 `~/.hq/skill-path`；再没有就用 shell 查找：`find ~/.claude/skills ~/.claude/plugins ~/.agents/skills ~/.dsh/skills ~/.config/opencode/skills ~/.cursor/skills ~/.gemini/skills ~/.gemini/extensions/hq-orchestrator/skills .claude/skills .agents/skills .dsh/skills .opencode/skills .cursor/skills .gemini/skills -path '*hq/SKILL.md' 2>/dev/null | head -1`，取其目录。
2. 读 `<hq>/SKILL.md`（主流程：本次运行按它执行）、`<hq>/references/stages/common.md`（阶段通用规则：产物目录、编号、模式、评审、决策）、`<hq>/references/backlog-schema.md`（清单格式）、`<hq>/calibration.md`（打分和档位）。
3. 台账头部写 `stage: plan`。

## 参数

- `--release <版本名>`：只规划（或重排）到这个版本，例如只出 MVP。
- `--horizon <N>`：规划几个版本。默认 MVP 加后续 1–2 个版本；P2 需求可以不排（`release: null`）。
- `--import`：强制按第 6 节导入已有计划（发现了外来格式的计划时默认就是导入）。
- `--review-only`、`--rounds N`、`--panel 角色,…`：见 `common.md` 第 4、5 节。默认评审团：`architect,engineer,qa`；需求是本阶段自己整理的（没有需求文档）时加 `pm`。
- 其余文字是补充说明（如“先做 Web 端”“两周内上线”“一个人做”），写进台账头部，作为约束交给起草任务。

## 1. 输入

在 `docs_root`（`common.md` 第 2 节）和仓库里找：一页纸、需求文档、竞品调研、设计稿、架构和详细设计、ADR、已有的 `plan/backlog.json`、README，以及现有代码。

| 情况 | 做法 |
|---|---|
| 已有计划，但不是本格式（别的工具生成的任务图、表格、YAML 等） | **导入**（见第 6 节），不重新拆任务 |
| 需求文档是外来格式（对应表里 `prd` 为 `foreign`） | 正常规划；需求编号用原文件的编号（如 `REQ-001`），优先级按原文件的写法换算成 P0/P1/P2 |
| 有需求文档 | 正常规划。`/hq-prd` 写的需求文档有“需求索引”表时，直接用它作为 `requirements`（建议版本为 MVP 的放进 R1），先运行 `doc-check.py prd` 确认文档没有错误；有错误时照常规划，把错误列进“假设与待确认”，汇报里建议先修需求文档 |
| 只有想法描述、一页纸、截图或竞品资料 | 可以规划：需求索引由本阶段整理，在 roadmap 开头写明“需求未经评审”，评审团加 `pm`；汇报里推荐先运行 `/hq-prd` |
| 什么都没有，命令后面也没写 | 问用户一句：“要规划的产品或目标是什么？可以直接贴描述，或给文件路径。”这是本阶段唯一需要等用户的输入 |
| 有架构文档（`/hq-arch` 产出） | 任务的 `owns` 按模块 `M-xx` 和详细设计里的目录结构写；第 11 章“风险与待验证”的每一项排成先行的调研任务；有设计原型时，界面任务的验收标准引用页面 `P-xx` 和流程 `FL-xx` |
| 没有架构文档，但有代码 | 从代码推断模块（目录、包、服务），在 roadmap 里列出 |
| 没有架构文档，也没有代码（全新项目） | 第一个版本先排“技术选型和脚手架”任务（`kind: research` 或 `docs`，通常 T4），后面任务的 `owns` 写模块编号；汇报里推荐运行 `/hq-arch` |
| 已有代码实现了部分需求 | 只规划剩下的；已完成的需求在需求索引里标出，不再排任务 |

## 2. 任务图（hq 主流程第 2 步按这个模板拆）

| 步 | 内容 | kind | 典型档位 | 依赖 |
|---|---|---|---|---|
| p1 侦察 | 只读：读上游产物和代码，产出需求索引（编号、标题、优先级、出处、是否已实现）、模块清单（现有的和计划的）、技术约束、项目的测试和构建命令 | research | T2（大项目或多份上游时 T3） | - |
| p2 起草 | 按第 3 节写 `plan/roadmap.md` 和 `plan/backlog.json` | docs | T3（需求超过约 30 条或全新架构时 T4） | p1 |
| p3 检查 | 主会话运行 `python3 <hq>/scripts/backlog-check.py <backlog.json> --prd <需求文档>`，有错误就交回起草任务修改，直到没有错误 | - | - | p2 |
| p4 评审 | 评审团并行，按 `common.md` 第 5 节 | review | 按角色卡 | p3 |
| p5 修改 | 按分诊结果修改，再跑一次 p3 | docs | 同 p2 | p4 |
| p6 复核 | 第 2 轮评审，只在第 1 轮有 blocker 或 major 时做 | review | 同 p4 | p5 |

- **补全模式**（已有 backlog）：p1 额外比较清单和上游、代码：上游新增或改动的需求、代码里已经完成但清单还是 `todo` 的任务（改成 `done` 并写明依据）、`based_on` 是否过期。p2 只改需要改的部分，已发布的任务编号不改不复用。
- **只评审模式**：只做 p1、p3、p4，写评审记录。
- p1 的结论要压缩后再写进 p2 的说明（需求索引和模块清单可以直接附上），不要让起草任务重新读一遍全部代码。

## 3. 起草规则（写进 p2 的说明）

**版本**
- R1 是 MVP：验证核心价值需要的最小范围，加上全部 P0。
- 每个版本都能单独发布、给用户完整的价值：按功能纵向切（一个功能的数据、接口、界面、测试在同一个版本），不要横向切成“先做完全部后端再做前端”。
- 每个版本的 `exit_criteria` 可检验，并包含一次端到端冒烟。
- 版本内的顺序：脚手架、数据模型、共享接口、CI 这类前置任务在前；风险高或不确定的部分尽早，先排一个调研任务（`kind: research`）验证，实现任务依赖它。

**任务**
- 粒度约 15–120 分钟；难度单一（不要把机械改动和找根因放在一起）；并行任务的 `owns` 不重叠，共享接口单独拆成前置任务。这些和 hq 主流程第 2 步一致。
- 每个任务都有可检验的 `acceptance`，`verify_level` 和风险相符：数据、安全、并发、公开 API 用 `high`。
- 测试跟着代码任务走，每个代码任务自带测试；不要在最后排一个“补测试”任务。每个版本另排一个发布检查任务（`verify_level: e2e`），负责冒烟。
- 非功能需求（性能、安全加固、监控告警、备份恢复）和需求里列出的上线必需项（隐私政策、应用商店素材等）也要有任务覆盖。
- **打分**：按 `calibration.md` 的 5 维逐项打分，写进 `score`；`tier` 取分数线对应的档位。拿不准就按规则 9 上调，并在 `tier_note` 写 `bias:+1`。不考虑并发和预算（规则 11）。`est_min` 估实际干活的时间，不含等待审核的时间。
- 模糊度 2 分的需求：先拆一个调研任务，实现任务依赖它，实现任务的档位按调研后的预期打分。

**roadmap.md 内容**
1. 元数据（`common.md` 第 2 节）。
2. 总览表：版本、目标、包含的需求编号、任务数、累计预计用时、关键路径预计用时、档位分布。
3. 每个版本：目标；范围（需求编号）；不做什么；发布条件；任务表（编号、标题、依赖、档位、预计用时）；风险和应对。
4. 依赖图：Mermaid `flowchart`，每个版本一个 `subgraph`，节点写任务编号和短标题。
5. 需求覆盖表：需求编号、优先级、版本、对应任务。
6. 假设与待确认（`A-xx`）。

roadmap.md 和 backlog.json 不一致时以 backlog.json 为准；改动清单后同步更新 roadmap.md。

## 4. 完成标准（自检和评审都按这个清单）

1. `backlog-check.py` 没有错误；每条警告都已改掉，或在 `notes` / `tier_note` 里写明理由。
2. 每个 P0 需求在它所在的版本里有任务覆盖；P1 有覆盖，或写明推迟理由。
3. 每个版本能单独发布，`exit_criteria` 可检验，并包含端到端冒烟。
4. 每个任务约 15–120 分钟、难度单一、`owns` 明确、`acceptance` 可检验、`verify_level` 和风险相符。
5. 前置任务（脚手架、数据模型、共享接口、CI）排在依赖它们的任务之前；不确定的高风险部分有调研任务，并且排得早。
6. 每个任务的 `score` 逐项填写；`tier` 和分数线一致，上调的写了理由，下调的写了依据。
7. 非功能需求和上线必需项有任务覆盖。
8. roadmap.md 和 backlog.json 一致（版本、任务数、档位分布），依赖图能渲染。
9. 两份产物都写了 `based_on`；所有假设都列进“假设与待确认”。
10. 评审：没有未解决的 blocker；评审记录已写进 `reviews/plan-<YYYYMMDD>.md`。

## 5. 交付与汇报

- 产物在 `hq/<任务id>` 分支上，按 PLAYBOOK 授权合并（`common.md` 第 1 节）。
- run 记录写 `common.md` 第 8 节的阶段字段。
- 汇报（按 hq 主流程第 10 步，再加以下内容）：
  - 版本总览表（同 roadmap 第 2 项）和关键路径；
  - 评审轮次、各级问题数、未解决项；
  - 假设与待确认，每条附推荐选项；
  - 下一步：`/hq --backlog <backlog.json 路径> R1`（或直接说“执行 R1”）开始执行第一个版本；缺需求文档或架构文档时，同时建议运行对应的阶段命令。

## 6. 导入已有计划

项目已有别的格式的计划时（对应表里 `plan` 为 `foreign`），不重新拆任务，而是把它转成 `backlog.json`，让 `/hq --backlog` 能直接执行。

- **转换**（一个 T2–T3 子任务；计划很大时按版本或模块分几个任务并行，各写一段，最后合并）：
  - 编号、标题、依赖、负责的文件（`owns`）、验收标准、预计用时照原计划搬，**编号保留原样**（如 `DF-V1-BASE01`），需求编号用需求文档的原编号。
  - 原计划没有的字段按本技能第 3 节补：版本（原计划只有一个里程碑时就是一个版本）、`verify_level`、5 维打分 `score`。
  - 原计划有自己的难度分级时，写进 `tier_note`（如“原难度 D4”），作为打分的对照；两者明显不一致时以 5 维打分为准，在 `tier_note` 里写一句原因。
  - 原计划里的“假设与未决问题”搬进 `roadmap.md` 不需要写：原计划文件本身就是给人看的版本计划。
- **检查**：`backlog-check.py <backlog.json> --prd <需求文档>`，没有错误为止；警告逐条处理或写明理由。再核对任务数、总用时和关键路径与原计划一致，不一致时写明原因。
- **对应表**：`plan` 改成 `{"format": "hq", "skip": ["roadmap"], "source": "<原计划路径>"}`，然后运行 `stage-status.py --docs <docs_root> --record-source plan` 记下原计划的指纹。原计划之后被改动，`stage-status.py` 会把计划阶段标成“上游已更新”，重新导入即可。
- 原计划文件不动。评审只做 1 轮，评审团 `engineer`、`qa`，只看转换有没有丢信息、打分是否合理。
