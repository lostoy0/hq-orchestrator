# HQ 上线检查（/hq-launch）

在你按下发布之前，把上线会出事的地方都找出来：功能是不是真的做完了、安全和隐私有没有底线问题、出了故障能不能恢复、能不能收到钱、有没有人知道你上线了。**结论只是建议，发布由你决定。本技能不部署、不发布、不付费、不注册外部账号。**

## 先读

1. 找 hq 技能目录 `<hq>`：本文件同级的 `../hq/`（里面有 `SKILL.md`）；没有就读 `~/.hq/skill-path`；再没有就用 shell 查找：`find ~/.claude/skills ~/.claude/plugins ~/.agents/skills ~/.dsh/skills ~/.config/opencode/skills ~/.cursor/skills ~/.gemini/skills ~/.gemini/extensions/hq-orchestrator/skills .claude/skills .agents/skills .dsh/skills .opencode/skills .cursor/skills .gemini/skills -path '*hq/SKILL.md' 2>/dev/null | head -1`，取其目录。
2. 读 `<hq>/SKILL.md`（主流程）、`<hq>/references/stages/common.md`，以及本文件同级的 `template-checklist.md`（46 项标准清单）、`template-runbook.md`。
3. 台账头部写 `stage: launch`。

## 参数

- 命令后面的文字：补充说明（如“先只在国内上线”“这次不开付费”），作为约束写进台账头部。
- `--release <版本>`：检查哪个版本。默认取计划清单里第一个还有任务没发布的版本；没有计划清单时检查当前默认分支。
- `--market <地区>`：目标市场，决定合规项怎么查。没给时按需求文档判断。
- `--check-only`：只检查，不起草材料。
- `--panel 角色,…`：改检查分工（见第 2 节）。

## 1. 输入

需求文档（P0 需求、非功能需求、上线必需项核对、埋点、商业化；外来格式的按内容读，编号照用，见 `common.md` 第 10 节）、设计原型、架构和详细设计、计划清单（这个版本的任务状态）、PLAYBOOK“项目事实”（测试、构建、lint 命令）、代码和配置（部署、CI、环境变量示例、依赖清单）、已有的法律文本和上线材料。

- 没有需求文档或计划清单时照常检查，相关项写“待人工确认”，在“假设与待确认”写明依据不足，汇报里建议先补文档。
- 什么都没有（空仓库）时，告诉用户上线检查需要已经开发的产品，建议先运行 `/hq-blueprint` 或 `/hq`。

## 2. 任务图（hq 主流程第 2 步按这个模板拆）

| 步 | 内容 | 角色 | 典型档位 | 依赖 |
|---|---|---|---|---|
| c1 侦察 | 只读：确定版本范围、目标平台和市场、有没有付费和个人信息；把 46 项里明显不适用的标出来（写原因）；找出测试、构建、审计用什么命令 | - | T2 | - |
| c2 产品与质量（A、B） | 对照需求和计划逐项核对；跑全量测试、构建、lint；核心流程冒烟（有原型流程时按流程在真实产品上走一遍，有 Playwright 就自动走） | `qa`、`pm` | T2 | c1 |
| c3 安全（C） | 跑依赖漏洞审计（`npm audit`、`pnpm audit`、`pip-audit`、`cargo audit`、`govulncheck` 中项目适用的）、密钥扫描（有 `gitleaks` 用它，否则 `git grep` 常见密钥格式，含历史）；读认证、鉴权、输入校验相关代码 | `security` | T3 | c1 |
| c4 隐私与合规（D） | 对照实际收集的数据检查法律文本和同意流程；按目标市场列资质和平台要求；扫开源依赖许可证 | `legal` | T3 | c1 |
| c5 运维（E） | 读部署、CI、配置、监控和备份相关文件；核对运维手册 | `ops` | T2 | c1 |
| c6 运营、商务、发布（F、G、H） | 核对埋点和看板、首次体验、渠道和素材、定价和收费流程、发布说明 | `growth`、`business` | T2 | c1 |
| c7 起草 | 起草缺少的材料（第 4 节），`--check-only` 时跳过 | 按材料 | T2（法律文本 T3） | c2–c6 |
| c8 汇总 | 主会话把 c2–c6 的结果填进 `launch/checklist.md`，按规则写结论；运行 `python3 <hq>/scripts/doc-check.py launch <checklist.md>`，有错误就改 | - | - | c2–c7 |
| c9 抽查 | 只读：独立子会话随机抽 5 条“通过”，按证据重新确认；有不符的改成“不通过”或“待人工确认”，再跑一次 c8 的检查 | `qa` | T2 | c8 |

- c2–c6 并行；没有付费的产品不派 `business`，没有个人信息又不对外的工具可以缩小 c4。
- 每项结果按 `template-checklist.md` 的规则填：**“通过”必须有证据**（命令和输出摘要、文件位置、截图），没证据的不算通过。
- 只有在生产环境、外部账号或用户电脑上才能确认的项（备案、商店后台、云账单提醒、真实支付），写“待人工确认”，在“需要你确认”里写清去哪里看、看什么。
- 跑命令只为验证：不部署、不推送、不改生产配置；扫描结果里出现的密钥只写位置和类型，不写值。

## 3. 结论规则

- 有任何“不通过”且严重程度为 `blocker` → **暂不上线**。
- 否则，有“不通过”的 `major`，或“待人工确认”的 `blocker` → **有条件上线**，条件逐条写出（确认了什么、修好了什么才能发）。
- 都没有 → **可以上线**。
- 严重程度按角色卡的否决权定：安全或隐私底线、收费流程不通、无法回滚的数据变更、P0 需求没做完，都是 `blocker`。
- 法律文本只有草稿、未经专业人士审核时，L-18、L-19（有付费时还有 L-43）记“待人工确认 + blocker”。

## 4. 起草材料（缺什么起草什么）

放在 `<docs_root>/launch/` 下，已有的只补缺，不覆盖：

| 材料 | 什么时候起草 | 角色 |
|---|---|---|
| `runbook.md` 运维手册 | 总是（按 `template-runbook.md`） | `ops` |
| `release-notes.md` 发布说明 | 总是：这个版本给用户的更新内容和已知问题 | `pm` |
| `launch-plan.md` 上线运营计划 | 对外产品：首批用户渠道、上线公告草稿、第一周看哪些数据、反馈怎么收 | `growth` |
| `legal/privacy-policy.md`、`legal/terms.md` | 产品没有这两份文本时 | `legal` |
| `legal/refund-policy.md` | 有付费时 | `legal`、`business` |
| `store-listing.md` 商店素材文案 | App 或小程序：名称、副标题、关键词、描述、截图说明、隐私标签填法 | `growth` |

法律文本按 `roles/legal.md`：按产品实际做法写，开头注明“草稿，未经法律专业人士审核，上线前必须审核”。

## 5. 完成标准

1. `doc-check.py launch` 没有错误：46 项都有结果，“通过”都有证据，结论不比规则更乐观，阻塞问题和需要确认的项都列出来了。
2. 能用命令验证的项实际跑过（测试、构建、依赖审计、密钥扫描），输出摘要写在证据里；跑不了的写原因。
3. 抽查（c9）的 5 条“通过”经重新确认无误，或已改正。
4. 需要用户确认的每一项都写清了怎么确认。
5. 缺少的上线材料已起草（`--check-only` 除外），法律文本标明是草稿。
6. 没有做任何部署、发布、付费、注册外部账号的操作。

## 6. 交付与汇报

- `launch/checklist.md` 和起草的材料在 `hq/<任务id>` 分支上，按 PLAYBOOK 授权合并（`common.md` 第 1 节）。
- run 记录写 `common.md` 第 8 节的阶段字段（`stage: launch`）。
- 汇报（按 hq 主流程第 10 步，再加以下内容）：
  - 结论和一句话理由；
  - 阻塞问题（每条：问题、怎么修；能派 `/hq` 修的，给出可以直接用的目标描述）；
  - 需要你确认的事项（每条：去哪里看、看什么）；
  - 八个方面各自的通过 / 不通过 / 待确认数；起草了哪些材料；
  - 下一步：修完阻塞问题后再跑一次 `/hq-launch`；结论为“可以上线”时，按运维手册发布。
