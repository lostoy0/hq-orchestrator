# 角色卡

阶段技能派写作或评审子会话时，把对应角色卡的全文写进说明。角色卡只规定**从什么角度看、看哪些点**；用什么模型和思考深度按 `../../calibration.md` 打分决定，和角色无关。

| 角色 | 文件 | 否决权 | 常见用途 |
|---|---|---|---|
| 产品 | `pm.md` | 和需求、目标用户冲突的方案 | 写需求、评审设计和计划 |
| 交互与视觉设计 | `designer.md` | 无（体验问题最高记 major，流程走不通记 blocker） | 写设计、评审需求 |
| 架构 | `architect.md` | 实现不了或违背已定架构的方案 | 写架构、评审需求和计划 |
| 开发 | `engineer.md` | 按现状实现不了的方案 | 评审需求、设计、架构、计划 |
| 测试 | `qa.md` | 无法验收的需求或任务 | 评审需求、设计、计划 |
| 市场与竞品研究 | `researcher.md` | 结论和来源不符 | 写竞品调研、核查事实 |
| 运维与可靠性 | `ops.md` | 无备份或无法回滚的数据变更、密钥进代码 | 评审架构；有部署、高可用或成本要求时选 |
| 安全 | `security.md` | 安全或隐私底线问题 | 评审需求、架构；涉及账号、支付、个人信息时必选 |

通用要求（每张卡都适用）：
- 只就自己的角度提意见；别的角度的问题最多记一条 `minor` 并写“建议由 <角色> 确认”。
- 每条意见要有依据（产物位置、上游原文、清单条目），没有依据的不写。
- 意见格式、条数上限和严重程度定义见 `../stages/common.md` 第 5 节。
- 增长运营、商务定价、法务合规的角色卡随 `/hq-launch` 一起加（见 `docs/design-stages.md` 第 8 节）。
