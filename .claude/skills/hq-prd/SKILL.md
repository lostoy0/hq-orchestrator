# HQ 需求阶段（/hq-prd）

按上线标准写出一份能直接拿去做设计、架构和计划的需求文档：用户是谁、首版做什么不做什么、每个功能怎么算做完、怎么赚钱、怎么衡量成败、上线前哪些基础功能不能漏。**本阶段不做技术设计，也不画设计稿。**

## 先读

1. 找 hq 技能目录 `<hq>`：本文件同级的 `../hq/`（里面有 `SKILL.md`）；没有就读 `~/.hq/skill-path`；再没有就用 shell 查找：`find ~/.claude/skills ~/.claude/plugins ~/.agents/skills ~/.codex/skills ~/.dsh/skills ~/.config/opencode/skills ~/.cursor/skills ~/.gemini/skills ~/.gemini/extensions/hq-orchestrator/skills .claude/skills .agents/skills .codex/skills .dsh/skills .opencode/skills .cursor/skills .gemini/skills -path '*hq/SKILL.md' 2>/dev/null | head -1`，取其目录。
2. 读 `<hq>/SKILL.md`（主流程：本次运行按它执行）、`<hq>/references/stages/common.md`（阶段通用规则）、`<hq>/references/roles/pm.md`，以及本文件同级的 `template.md`（文档格式）。要做竞品速览时再读同级的 `../hq-research/SKILL.md` 和 `../hq-research/template.md`。
3. 台账头部写 `stage: prd`。

## 参数

- 命令后面的文字：补充说明（目标用户、平台、时间、预算、必须有或不要的功能等），作为约束写进台账头部。
- `--from <路径>`：指定输入（文件、目录、截图），可以写多次；不写时自动在项目里找。
- `--scope <模块>`：只新写或补全某个模块的功能需求，其余章节只做一致性检查。
- `--no-research`：没有竞品调研报告时也不做竞品速览（见第 2 节）。
- `--convert`：已有需求文档不是本模板格式时，另写一份本模板格式的文档（默认是接管，不另写）。
- `--ask`：侦察后先把待决定事项（`D-xx`）问一次，等回答再写（`common.md` 第 6 节）。
- `--review-only`、`--rounds N`、`--panel 角色,…`：见 `common.md` 第 4、5 节。默认评审团：`designer`、`architect`、`qa`，第 4 个按产品选：涉及账号、支付、个人信息时加 `security`（多数产品都涉及），否则加 `engineer`；已有代码时 `engineer` 优先于 `architect`。

## 1. 输入

在 `docs_root`（`common.md` 第 2 节）、`--from` 和仓库里找：一页纸、想法描述、已有需求文档、竞品调研报告、设计稿和截图、竞品截图、README，以及现有代码。

| 情况 | 做法 |
|---|---|
| 只有想法、一页纸、截图或设计稿 | 新建。截图和设计稿由侦察任务转成文字描述（页面、流程、功能点），宿主读不了图片时请用户补一两句文字说明 |
| 已有按本模板写的需求文档 | 补全模式：按完成标准和 `doc-check.py` 找缺项，只增改不删 |
| 已有需求文档，但不是本模板格式（别的工具或团队自己的模板） | 按 `common.md` 第 10 节**接管**：先建或读对应表 `hq-artifacts.json`，再做接管评审（按完成标准判断内容，不看格式），把结果用 `stage-status.py --record-audit` 记下；已冻结的只写提案，没冻结的在原文件里按原结构补缺口，编号照用。不另写一份 hq 格式的需求文档；只有带 `--convert` 时才写到 `product/prd.md`（被占用时写 `product/prd-hq.md`），原文件不动，对应表改指向新文件 |
| 已有代码 | 已经实现的功能也写成需求，在“备注”写“已实现（位置）”，便于后面只规划剩下的 |
| 什么都没有，命令后面也没写 | 问用户一句：“要做的产品是什么？一两句话描述，或给文件路径。”这是本阶段唯一需要等用户的输入 |

## 2. 竞品输入

- 有 `research/competitors.md`：直接用它的“对需求的建议”“定价对比”“机会点”。`updated` 超过 90 天时，在“假设与待确认”记一条，建议重跑 `/hq-research`。
- 没有报告，也没有 `--no-research`：加一个竞品速览任务（第 3 节 d2），按 `/hq-research` 的规则做缩小版：`--n 5 --deep 1`，产出同样格式的 `research/competitors.md`（元数据如实写 `competitors_target: 5`、`deep_target: 1`），并用 `doc-check.py research` 检查；评审只做 `researcher` 事实核查 1 轮。
- 不能联网，或带了 `--no-research`：跳过；在“假设与待确认”记“未做竞品调研”，差异化和定价写成假设，汇报里建议运行 `/hq-research`。

## 3. 任务图（hq 主流程第 2 步按这个模板拆）

| 步 | 内容 | kind | 典型档位 | 依赖 |
|---|---|---|---|---|
| d1 侦察 | 只读：读全部输入和代码，产出产品目标、目标用户、核心场景、已有功能（含已实现的）、约束、输入之间的冲突、候选的待决定事项 | research | T2 | - |
| d2 竞品速览 | 只在第 2 节要求时做 | research | 按 `/hq-research` | d1 |
| d3 骨架与关键决策 | 写第 1、2、6 章（概述、范围、商业化）的完整内容；列出全部功能和非功能需求的编号、标题、模块、优先级，给每个模块分好编号段（如账号 F-001–F-019、记账 F-020–F-039）；列出 `D-xx`，每条附推荐 | docs | T3（全新产品、商业模式未定时 T4） | d1、d2 |
| d4 功能详写 | 按模块写第 4 章的功能需求；功能超过约 15 个时每个模块一个任务并行，每个任务只写自己的编号段；另一个任务写第 5 章非功能需求 | docs | T2–T3 | d3 |
| d5 合稿 | 合并 d4；写第 3、7–11 章（用户旅程、埋点、上线必需项、风险、假设与待确认、需求索引）；统一术语，检查前后一致 | docs | T3 | d4 |
| d6 检查 | 主会话运行 `python3 <hq>/scripts/doc-check.py prd <需求文档>`，有错误就交回 d5 修改，直到没有错误 | - | - | d5 |
| d7 评审 | 评审团并行，按 `common.md` 第 5 节 | review | 按角色卡 | d6 |
| d8 修改与复核 | 按分诊结果修改，再跑一次 d6；第 1 轮有 blocker 或 major 时做第 2 轮评审 | docs / review | 同 d5 / d7 | d7 |

- d3 是整份文档里分量最重的一步：目标用户、首版范围、商业模式定错了，后面写得再细也白写。主会话按 `common.md` 第 6 节的优先级复核 d3 的结论，再派 d4。
- 带 `--ask` 时，d3 之后先问 `D-xx`，等回答再派 d4；不带时按推荐继续，阶段结束时一次问。
- 产品小（功能少于约 8 个）时，d3、d4、d5 合成一个任务。
- `--scope <模块>`：d3 只补这个模块的功能列表，d4 只写这个模块，d5 只更新需求索引、上线必需项和受影响的章节。

## 4. 写作规则（写进 d3–d5 的说明）

**范围**
- 首版（MVP）只放验证核心价值需要的功能，加上不做就不能上线的基础功能。P0 = 不做就不能上线；P1 = 首版应该有；P2 = 以后再说。功能多于 5 个时，P0 一般不超过一半。
- 写清“不做什么”：用户可能期待、但首版不做的功能，各写一句理由。

**每个功能**（第 4 章，格式见模板，`doc-check.py` 会检查）
- 用户故事写成“作为…，我想…，以便…”。
- 验收标准可检验，包括边界和异常（空输入、超长、重复提交、断网、超时、并发修改）。
- 界面状态写全：空、加载、错误、无权限、首次使用；不适用的写原因。
- 写权限（谁能用）、埋点（事件名）、依赖（其他功能或外部服务）。
- 只写要什么，不写怎么实现；性能、安全这类要求写进非功能需求。

**体验**：默认按简洁易懂、步骤少、默认值合理、复杂功能逐步展开的方向写；遵守目标平台的规范；核心流程写清从入口到完成的每一步（第 3 章用 Mermaid 画）。

**非功能需求**：至少覆盖性能、安全、隐私；按产品补可用性、兼容、可访问性、国际化、合规、可观测。要求写成可量化的数字。

**商业化**（第 6 章）
- 收入方式、定价假设（引用竞品定价 C-xx）、免费和付费的边界、付费点和转化路径、粗略的单位经济（获客成本、客单价、毛利）。
- 付费墙不能挡在用户体会到核心价值之前。
- 商业模式的根本选择（免费 / 订阅 / 一次性付费 / 广告）和价位区间没定时，记 `D-xx`，按推荐写，相关内容集中写在本章，改选时只改这里。

**上线必需项**（第 8 章）：模板里每一行都要写结论：包含（对应编号）/ 不做：原因 / 不适用：原因。这张表用来防止漏掉注册登录、找回密码、注销账号、隐私政策这类不起眼但上线必需的功能。

**需求索引**（第 11 章）：列出全部 `F-`、`NFR-`，优先级和正文一致，“建议版本”写 MVP 或后续版本名。`/hq-plan` 直接读这张表。

## 5. 完成标准（自检和评审都按这个清单）

1. `doc-check.py prd` 没有错误；每条警告都已改掉，或在“假设与待确认”里写明理由。
2. 目标用户、核心场景、价值主张写清，每个功能都能追溯到它们；和竞品的差异有依据（有调研报告时引用 C-xx）。
3. 首版范围最小但完整：P0 功能合起来能走通核心流程；“不做什么”写了。
4. 每个功能有用户故事、可检验的验收标准（含边界和异常）、完整的界面状态、权限和埋点。
5. 非功能需求可量化，至少覆盖性能、安全、隐私。
6. 商业化写了收入方式、定价假设、免费与付费边界、付费点；根本选择没定的记成 `D-xx`。
7. 成功指标有北极星指标和护栏指标，写了目标值和口径；埋点能支撑这些指标。
8. 上线必需项每一行都有结论。
9. 需求索引完整，和正文一致。
10. 所有假设和待决定事项都列进“假设与待确认”；有未决的 `D-xx` 时 `status` 不是 `approved`。
11. 评审：没有未解决的 blocker；评审记录已写进 `reviews/prd-<YYYYMMDD>.md`。

## 6. 交付与汇报

- 需求文档在 `hq/<任务id>` 分支上，按 PLAYBOOK 授权合并（`common.md` 第 1 节）。做了竞品速览时，报告一起交付。
- run 记录写 `common.md` 第 8 节的阶段字段。
- 汇报（按 hq 主流程第 10 步，再加以下内容）：一句话产品定位；首版范围（P0 / P1 / P2 各几个）；商业模式；评审轮次、各级问题数、未解决项；待决定事项 `D-xx`（每条附推荐，请用户拍板）和其他假设；下一步：运行 `/hq-plan` 拆成版本计划（设计和架构阶段技能上线后，先跑 `/hq-design`、`/hq-arch`）。
